# Changelog

The bundle's version history: one section per script, newest version first. Any change to one script
bumps all of them to the same version number. Everything up to v93 was built privately and published
as one release. Entries from v53 on are the notes as they were written at the time; earlier ones
were reconstructed afterwards (the note below says how).


The Chromebook bundle is four scripts that share one version number: dev-setup, dev-test, dev-init
and dev-demo. A change to any of them bumps all four, so a version can appear under a script with no
change of its own ("version bump only").

Until v81 each script kept this history in comments at the top of its file. Since v81 it lives here,
one section per script, and each script's header points to this file. Comments that explain a
particular line of code, tagged with the version that added them, stay in the scripts.

The bundle started as one script. Versions 1 to about 49 were built with Gemini: a single installer,
named setup.sh at first and dev-setup-chromebook from v17. Around v50 the work moved to Claude, and the
other scripts followed: the test script by v52, init in v53 and demo in v75. The entries before v53 were
reconstructed afterwards, from notes on the Gemini-era conversations and from the version-tagged comments
in the scripts. They are coarser than the rest, and a version with no surviving notes says so.

- **v93:** the retro guests ready for Delphi 3, 4, 5, 6 and 7, the laptop network over Tailscale, and five database fixes (new command `delphi`; no new flags). (1) Retro (install-retro), from the v93 plan's seven items. Program CDs: each guest gets ~/<guest>/install/apps (win31's was there already) for .iso files, and the app CD is F: in every guest: win31 mounts it through DOSBox-X's CD support beside D: (install/apps itself), win95 as the IDE secondary slave beside the Windows CD (E:), winnt40 and win2000 in their second CD drive (ide1-cd1), which now always exists (empty when there is nothing for it) so a CD can be put in later. '<guest> cd FILE.iso|NAME|eject|list' picks it (kept in ~/<guest>/apps-cd; the last choice, else the first .iso in install/apps); winnt40 and win2000 swap it while running, and 'cd --windows FILE|eject' swaps their Windows CD (E:), which v92's 'cd' did; win31 and win95 take a new choice at the next start (DOSBox-X cannot swap from outside). A service-pack .iso in install/ rides in the second drive only when no app CD is there (as in v92). Two disk sizes are settings, read when a disk is created and never before: RETRO_EXCHANGE_MB (default 1024, 64-2047; v92 made 512 MB) and RETRO_WIN95_DISK_MB (default 2048, 512-8192; v92 made 1024 MB), from secrets.env or the command line for one run (RETRO_EXCHANGE_MB=512 win2000 setup; the command line wins); an out-of-range value stops the command before anything is made. A disk that exists is never resized: the exchange disk's size and layout are read back from its own boot sector, a different setting gets a one-line note, '<guest> exchange info' shows size, layout and free space, and '<guest> exchange recreate [--yes]' rebuilds it empty at the setting after offering to copy its files out first (as 'get' does); RETRO_EXCHANGE_HEADS=255 makes a new exchange disk with 255 heads, the fallback should a guest misread a big 16-head disk. 'retro sizes' prints the sizes in effect and each disk's, and setup's retro summary prints the same. win95's hdd.img is now made by IMGMAKE in a short windowless DOSBox-X run of its own: in the same session as the mounts, a second CD on the secondary channel left DOSBox-X 2024.03 stuck after IMGMAKE. (2) Laptop network (install-lan, install-lan-share) over Tailscale, as agreed on Oct 5 and Oct 8 2026: install-lan installs Tailscale from pkgs.tailscale.com (the keyring and list Tailscale's install.sh writes; a NOTICE when unreachable) and sets normal mode, FLAGS="--tun=tailscale0" in /etc/default/tailscaled (tailscaled had picked userspace networking in this VM); joining is dev-init's. The 'lan' command: the /etc/hosts block gives each laptop NAME.internal beside its name (Ollama on 127.0.0.1 answers a plain laptop name as Host with 403 and accepts .internal; LAN_SHARE stays the one list of shared services); 'lan share apply' publishes every LAN_SHARE port with 'tailscale serve --bg --tcp=PORT tcp://localhost:PORT' (as Tailscale's operator, else through sudo), removes only ports it published itself (~/.config/dev-lan/served.tsv; a port published by hand, such as a one-off 8000, is left alone and listed), and stops the v84 relay; 'lan share off/on' unpublishes and republishes them (off is remembered, so a later apply publishes nothing until 'on'); 'lan share' shows Tailscale's state, tailscale0's address, each port published or not, whether its service runs here, the .internal URL for Ollama and the site-name note for DDEV; 'lan share ports' says no ChromeOS forwards are needed. New 'lan probe [--tsv] NAME [PORT...]': every known port is tried at once, then each one that accepts gets one exchange in its own protocol, no login (HTTP with the Host a client sends, NAME.internal for Ollama, a TLS handshake on 8443, a TDS pre-login, a TNS connect, an anonymous LDAP bind, a Redis PING, a MongoDB hello, an HTTP/2 preface for Qdrant's gRPC): up, down (accepted then closed: 'tailscale serve' accepts while the service behind it is stopped), refused, or forbidden (Ollama's 403). New 'lan path [NAME...]': 'tailscale ping' says direct or through a DERP relay. 'lan url' gives Ollama as http://NAME.internal:11434.
